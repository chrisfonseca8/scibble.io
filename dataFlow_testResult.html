part 1

Request lifecycle and state transitions

1
Room instantiation (REST)
Client issues a POST /rooms request with a display name payload. The server generates a UUID for the room and a UUID for the player, persists a room record to Redis (hash key room:{id}) with status enum WAITING, and returns both IDs synchronously. This is a stateless HTTP request/response cycle — no persistent connection or handshake occurs at this stage.
2
Join validation (REST)
Each subsequent client sends a POST /rooms/:id/join request. The server performs three synchronous validations against the Redis record — existence check, capacity check (currentPlayers < maxPlayers), and status check (WAITING) — then atomically appends the player to the room's player set. On reaching capacity, the room's status flag flips to closed-for-join to prevent race conditions on the last open slot.
3
WebSocket handshake and auth
Each client upgrades its connection via a WebSocket handshake and emits an identify event carrying its room ID and player ID. The server authenticates the pair against the Redis room membership set, binds the socket instance to the player ID in an in-memory connection map, and broadcasts a player_joined event to all other sockets in that room namespace.
4
Lobby state — pre-game
Clients idle in a WAITING state pending a host-triggered start_game event. Authorization middleware restricts update_settings and start_game mutations to the socket flagged as isHost; all other clients receive read-only state broadcasts via lobby_update.
5
Turn initialization
The server's turn scheduler selects the next drawer via round-robin index and emits a word_choices event containing three candidate strings — scoped only to that socket via a targeted emit, not a room broadcast. All other clients receive a generic awaiting_word_selection state. A server-side timeout timer triggers a fallback random selection if no select_word event is received within the threshold.
6
Round state transition
On word selection, server transitions room status to IN_ROUND and broadcasts a round_start payload containing only word length (masked string, e.g. _ _ _ _ _) to non-drawer sockets, and the plaintext word to the drawer's socket only. A server-authoritative countdown timer begins, synced to clients via periodic tick events.
7
Stroke streaming and guess validation
Only the drawer's socket is authorized to emit stroke events, which the server relays to all other sockets in the room with sub-100ms target latency — no server-side persistence of stroke data beyond the active turn. Guess payloads sent via chat_message are intercepted server-side, string-normalized, and diffed against the answer before being either (a) rebroadcast as plaintext chat if incorrect, or (b) suppressed from broadcast and replaced with a correct_guess system event if matched — preventing answer leakage through the chat relay. Point deltas are computed server-side for both guesser and drawer and applied to the session's in-memory score table.
8
Turn teardown / game termination
A turn terminates on countdown expiry or when the guesser set equals the eligible-player set. Server emits turn_end with the updated score table, increments the turn counter, and re-invokes the turn scheduler. Once turnCount >= maxTurns * playerCount, the server transitions room status to FINISHED and emits a game_over event with the final leaderboard computed server-side.
×
Disconnect handling
A disconnect event can fire from any state above and is handled via a dedicated cleanup routine. Drawer disconnect mid-round triggers immediate turn_end (forced termination, bypassing normal exit conditions). Non-drawer disconnect decrements the active-player count used in guess-completion checks. Host disconnect triggers host-reassignment logic (next-in-index promotion). If the resulting player set is empty, the room's TTL is set to expire immediately and the Redis key is evicted, along with its in-memory connection map entries.

Bottleneck analysis: at 50 concurrent rooms (300 sockets), REST throughput and WS handshake completion both hit 100% — no dropped connections, no failed state transitions. Scaling to 100 rooms (600 sockets) held REST success at 100%, but WS handshake completion degraded to 87% (524/600), producing a correlated drop in successful IN_ROUND transitions (87/100 game-starts). REST endpoints (room creation, join validation) show no degradation under this load — the bottleneck is isolated to the WebSocket upgrade/handshake path under a connection-burst pattern, likely event-loop or file-descriptor contention at the point where hundreds of upgrade requests arrive within the same window. This localizes the next optimization target to connection-handling concurrency rather than the REST layer or Redis access patterns.
